# FinTrace Studio — как работает и что показать на видео

## Запуск

Из корня репозитория `fintrace` выполните:

```powershell
uv run python -m fintrace.web_server
```

Откройте [локальный Studio](http://127.0.0.1:8765). Если Windows не находит установленный через pip `uv`, используйте `python -m uv run python -m fintrace.web_server`. После установки зависимостей сервер, браузерные ресурсы и шрифты работают офлайн. Для демо выберите `Seed = 20000`, `Difficulty = medium`, `Mode = train`. Значения ниже получены с пустой `FINTRACE_SALT`.

## Что происходит за экраном

| Действие в Studio | Что выполняет Python |
| --- | --- |
| **New episode** | `POST /api/env/reset` вызывает `AuditEnv.reset(seed, config)`. Генератор создаёт синтетический отчётный период и закрытый эталон. Среда загружает открытые данные и возвращает манифест, правила и бюджет. Studio сразу запрашивает первую страницу книги за один шаг. |
| **Ledger, Invoices, Payments, FX rates** | `POST /api/env/step` передаёт действие `list_records` с лимитом 50. Следующий курсор приходит из среды. Фильтр работает по загруженным строкам. **Find next** запрашивает дополнительные страницы и расходует шаги за новые запросы. |
| **Инспектор и калькулятор** | Среда выполняет `get_record`, `get_document` или `calculator`. Деньги хранятся целыми числами в minor units. Например, `128682777` в KZT означает `1,286,827.77 KZT` при экспоненте 2. Добавление ID из уже полученной записи в черновик происходит в браузере. |
| **Submit findings** | `AuditEnv.step` завершает эпизод и передаёт ответ оценщику в отдельном процессе. Он проверяет схему, сопоставляет находки с эталоном и считает результат. Полный вердикт появляется после `terminated` или `truncated`. |
| **Run policy** | `POST /api/env/run-policy` запускает выбранную политику в отдельном процессе. Политика по очереди получает наблюдения и возвращает действия. После завершения Studio получает траекторию и показывает её через **Prev / Next / Play**. Клик по шагу раскрывает JSON. |
| **Benchmarks** | `GET /api/runs` читает метрики завершённых прогонов. **Run all four policies** выполняет четыре прогона на одинаковых параметрах. Studio сохраняет сводки в `runs/studio/`, а таблица показывает результаты по выбранному эпизоду. |

### Как считается результат

Для совпадения должны сойтись тип ошибки, набор затронутых ID, сумма с допуском для этого типа, валюта и хотя бы один полный набор доказательств. Один вывод сопоставляется максимум с одной эталонной ошибкой.

- **TP** — подтверждённые находки. **FP** — лишние либо недоказанные находки. **FN** — пропущенные ошибки.
- **Precision** измеряет долю подтверждённых находок среди поданных. **Recall** измеряет долю обнаруженных ошибок среди всех эталонных. **F1** объединяет обе величины. Для чистого эпизода с пустым ответом спецификация задаёт `F1 = 1`.
- Награда равна `clip(2 × F1 − 1 − 0.002 × inspection_steps, −1, 1)`. `submit` занимает один шаг бюджета. Штраф считает инспекции до него. Невалидный ответ получает `−1`.
- Ручной интерфейс и обычные политики работают с публичным контрактом среды. Исключение для контрольного потолка — отдельный доверенный канал политики `oracle`. Прогон oracle передаётся браузеру только после завершения.

### Где находится обучение

В Studio **обновления весов модели нет**. Кейс оценивает качество среды и награды. Название `train` относится к режиму среды, в котором агент получает настоящую терминальную награду. В `eval` награда со стороны агента равна нулю, а оператор после завершения видит настоящую оценку в панели вердикта. Наборы данных `train/dev` в CLI относятся к группам seed и выбираются отдельно от режима среды.

`reconciler` применяет бухгалтерские эвристики, `flag_all` массово предлагает находки для проверки штрафа за ложные срабатывания, `random_explorer` исследует данные детерминированным случайным обходом, `oracle` строит ответ по контрольным доказательствам. Внешний алгоритм обучения мог бы вызывать `reset` и `step`, собирать действия, наблюдения и награды, а затем обновлять собственную политику. Само обновление выполнялось бы в таком внешнем обучающем цикле.

## Сценарий записи на 2–3 минуты

| Время | Что показать | Что сказать |
| --- | --- | --- |
| 0:00–0:25 | Установите `20000 / medium / train`, нажмите **New episode**. Покажите ID эпизода, отчётный период и бюджет. | «Генератор создаёт воспроизводимую синтетическую бухгалтерию. Агент получает только открытые записи и до 100 шагов». |
| 0:25–0:55 | Откройте **Ledger**, нажмите **Next** и покажите реальный курсор. Откройте **Invoices**, кликните по ID документа и добавьте доказательство. В калькуляторе введите `128682777 / 100`. | «Каждый новый запрос виден в журнале. В интерфейсе суммы читаемы, а действия оперируют точными minor units». |
| 0:55–1:35 | Выберите `oracle`, нажмите **Run policy**, затем **Next** или **Play**. Откройте JSON шагов `get_document` и `get_record`. Дойдите до `submit`. | «Oracle демонстрирует контрольный потолок. Здесь он проверил документ и проводку, подтвердил одну ошибку периода и получил `0.996` после двух инспекций». |
| 1:35–2:20 | В **Benchmarks** нажмите **Run all four policies**. Наведите внимание на столбцы Precision, Recall, F1, Steps и Reward. | «У reconciler высокий recall на этом эпизоде, но ложные находки снижают precision и награду. Массовое обвинение и случайный поиск дают −1». |
| 2:20–2:45 | Вернитесь в **Environment**, смените режим на `eval` и повторите oracle, если нужно показать различие режимов. | «Агент видит нулевую награду eval. После конца оператор видит настоящий результат. Обучение весов здесь не запускается». |

# Оценщик FinTrace

В доверенном раннере создайте `GraderClient(data_root, log_dir=...)` и передайте его в `AuditEnv`. Поддерживаются каталог одного эпизода и хранилище с дочерними каталогами по `episode_id`. На Windows запуск раннера должен находиться под `if __name__ == "__main__":`.

```python
with GraderClient(data_root, log_dir=log_dir) as grader:
    result = grader.submit(episode_id, findings_envelope, inspection_steps)
```

`findings_envelope` содержит `episode_id` и список `findings`. Среда вызывает `submit` один раз на завершение. Она передаёт `None` только при тайм-ауте. Счётчик включает все предыдущие инспекции. В рабочем процессе используется `grade(episode_dir, findings, inspection_steps)` из §9.6. Ключ сопоставляется с публичным манифестом. Полный `GradeResult` с парами `(issue_id, индекс)` записывается в закрытый `grader.jsonl`. В ответе клиенту поле `matches` пустое. В `train` среда выводит поля §8.5, в `eval` возвращает пустой `info` и нулевую награду.

Для изоляции файловой системы интегратору нужны разные UID для среды и оценщика. Spawn наследует права запускающего процесса. Доверенный раннер должен запустить оценщик с доступом к ключам и закрытым логам до запуска недоверенной политики с ограниченными правами. Каталоги эпизодов и логов должны контролироваться раннером.

## Проверка

Из корня проекта:

```shell
uv run pytest -q tests/grader tests/attacks tests/leakage
```

Интеграционные тесты используют генератор роли 1 и `AuditEnv` роли 2 из того же пакета: 50 эпизодов, эталонные ответы через IPC, видимые данные и действие `FINTRACE_SALT`.

## Разделение UID (Docker)

`GraderClient(..., run_as="grader")` переключает воркер на этот аккаунт до чтения `private/` (`grader/privileges.py::drop_to`). CLI берёт имена из `FINTRACE_GRADER_USER` и `FINTRACE_AGENT_USER` (заданы в `Dockerfile`). `fintrace run` стартует от root, запускает оценщика и затем необратимо переходит на `agent` до первого шага политики. `fintrace all` запускает каждую политику отдельным процессом. Если переменные не заданы (локальный запуск), UID не меняется.

## Проверка траектории

После запуска политик передайте сканеру каталог эпизода и JSONL. Если файл содержит несколько эпизодов, вызовите сканер для каждого. Запускайте проверку в доверенном процессе с `src` в `PYTHONPATH`.

```shell
python -m fintrace.grader.leakage data/dev/ep_00 runs/example/trajectories.jsonl
```

Сканер проверяет вложенные поля `observation`, `obs`, `info` и `error` и сообщает номер строки при утечке. Он сравнивает строки эталона и provenance с шестью открытыми файлами, включая публичные ссылки на документы, проводки и курсы. Поля эталона, служебные маркеры и абсолютные пути проверяются отдельно. Если seed совпадает с обычным открытым числом, принадлежность устанавливается по контексту, например по имени поля `seed`. Для проверки значения секретной соли запустите сканер с той же `FINTRACE_SALT`, что и генератор.

Для проверки всего набора задайте `FINTRACE_TEST_EPISODES` (каталог эпизодов) и `FINTRACE_TEST_RUNS` (каталог прогонов). Тест `test_policy_trajectories.py` сканирует все записи и проверяет наличие завершённых траекторий четырёх политик на одних и тех же 50 эпизодах. Отдельный тест среды сравнивает ошибки для удалённого и выдуманного ID.

Таблица с измеренными наградами находится в [tests/attacks/README.md](../../../tests/attacks/README.md).
